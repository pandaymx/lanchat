# ADR-013: 持久化存储选 libSQL（纯 Go 驱动），不直连 modernc/sqlite

- 状态：✅ 已采纳（M5 持久化阶段落地实施）
- 日期：2026-09-06
- 关联：AGENTS.md §2 技术栈 / §8 环境（交叉编译、gomobile）

## 背景

M5 部署阶段需要把 hub 的消息/游标存储从 `pkg/store/memory` 换成持久化引擎。原 AGENTS.md §2 写的是 `modernc.org/sqlite`（纯 Go 无 CGO 的 SQLite 翻译版），选它的理由是 mattn/go-sqlite3 需要 CGO、会毁掉交叉编译与 gomobile bind。

用户拍板：直接集成 **libSQL**（SQLite 的开源 fork，Turso 维护），而不是裸用 modernc/sqlite。

## 决策

- 持久化引擎用 **libSQL**，驱动只用纯 Go 的 `github.com/tursodatabase/libsql-client-go`
  （其本地文件模式底层即 modernc sqlite，SQL 方言与文件格式与 SQLite 兼容）。
- **禁止** CGO 绑定 `github.com/tursodatabase/go-libsql`——硬约束不变：
  纯 Go、零 CGO、可交叉编译（linux/arm64、windows、gomobile bind 移动端）。
- 访问层走标准库 `database/sql`，手写 SQL（不引入 ORM，AGENTS.md §2）。
- Store 仍以 `pkg/core.Store` 接口面向业务层（ADR-002），libSQL 只是一个新的
  `pkg/store` 实现，`pkg/core` 零修改。

## 为什么是 libSQL 而不是裸 modernc/sqlite

- 本地模式零额外风险：纯 Go 驱动本地引擎与 modernc/sqlite 同源，可靠性等价；
- 保留升级路径：libSQL 支持 remote / embedded replica 模式，二期多设备同步
  （ADR-008 的全设备同步）有现成的同步原语可选，不用时不付任何成本；
- 与 SQLite 生态兼容：已有 SQLite 工具链、备份方式、SQL 方言全部沿用。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 裸 `modernc.org/sqlite` | 能用但无升级路径；libSQL 纯 Go 驱动本地模式与之同源，无理由不选 |
| `mattn/go-sqlite3` | CGO 依赖，毁掉交叉编译与 gomobile，AGENTS.md §8 已明确禁止 |
| CGO 版 libSQL（`go-libsql`） | 同上，CGO 一票否决 |
| Postgres/MySQL 外置库 | 违背 LAN 单机零部署目标，M5 不考虑 |

## 落地位置

- M5：新增 `pkg/store/libsql`（或 libsql 实现 `core.Store`），替换 hub 侧 memory store
- 落地时同步修改 AGENTS.md §2 存储行（modernc.org/sqlite → libSQL 纯 Go 驱动）

## 验证

- `CGO_ENABLED=0 go build` 全平台通过；`gomobile bind` 通过
- 交叉编译 linux/arm64 / windows/amd64 产物可直接运行
- 既有 `core.Store` 测试套件在 libSQL 实现上全绿
